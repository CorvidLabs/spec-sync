# Design

Add `AcceptanceManifestV1` and `SemanticSuccessionEvidenceV1` as optional fields on `VerificationRecord`. The manifest has an explicit schema version and strictly path-sorted unique entries. Each entry contains a normalized portable path, explicit kind, numeric mode, lowercase SHA-256 payload digest of the exact represented bytes, a domain-separated full-entry digest over path/kind/mode/payload digest, and a sorted unique owner list. Succession entries contain predecessor ID, portable path, one canonical owner module, predecessor full-entry digest, and successor full-entry digest. New closing digests add separate `acceptance-input-manifest-v1` and `semantic-succession-v1` frames. Empty `ChangeRecord.supersedes` uses `#[serde(default, skip_serializing_if = "Vec::is_empty")]`; absent verification manifest and succession fields use `#[serde(default, skip_serializing_if = "Option::is_none")]`. When new fields are empty or absent, persisted state JSON, verification JSON, definition digest bytes, and `closing_digest` follow the existing byte-for-byte algorithms.

Add a default-empty `supersedes` collection to `ChangeRecord`, populated only through a supported `change supersede` transition before definition approval. Each edge names one predecessor and explicit path/module/predecessor-digest obligations. It is part of the definition digest. Approval validates that every obligation exactly adopts a reconstructed predecessor manifest entry and owner. Acceptance emits succession evidence only for approved edge obligations whose module has a non-empty semantic delta and whose definition-signed `base_commit` is trusted, reachable, and an ancestor of the unique accepted-transition anchor. The old full-entry digest must match the base tree and the new full-entry digest must match the accepted-transition tree. The acceptance commit's immediate parent is not treated as the before tree because it normally already contains verified implementation bytes.

Build manifests and owners from one immutable post-delta acceptance snapshot. Canonical specs and companions own their canonical module. Production source paths own every canonical module whose `files:` mapping in that same snapshot exactly covers the path. Unmapped production source paths fail acceptance. Governed paths classified by the existing project source classifier as tests or fixtures, plus recognized delivery metadata, receive reserved exact-only owners that can never be successor-covered. This permits CHG43's own `tests/integration/change.rs` evidence without fabricating module ownership: a later edit requires audited reopen and fresh acceptance. Owner derivation never reads today's mutable canonical specs during later validation; legacy derivation reads the trusted historical tree.

Canonical validation rejects manifests above 100,000 entries, paths above 4,096 bytes, more than 1,024 owners per entry, or owner names above 256 bytes. Paths and owners must be strictly sorted and unique; canonical-owner sets must be non-empty; digests must be 64 lowercase hexadecimal characters. Supported kind/mode pairs are file with `100644` or `100755`, symlink with `120000`, gitlink with `160000`, and missing/non-file with zero. Symlinks hash exact portable UTF-8 target bytes and reject non-portable targets. Gitlinks hash the exact object ID bytes from the Git index/tree rather than inspecting a checked-out directory. Full-entry digests use `specsync.acceptance-entry.v1`. New manifest-based `acceptance_input_digest` values use the distinct `specsync.acceptance-manifest.v1` domain and are recomputed solely from canonical entry tuples; legacy records without a manifest retain the raw-content `specsync.acceptance-input.v2` algorithm.

Portable paths and symlink targets are validated as host-independent UTF-8 text rather than with host-native `Path` absoluteness rules. Project paths use forward-slash-separated non-empty normal components and reject leading or trailing separators, backslashes, dot components, control characters, and drive-prefixed forms. Symlink targets remain allowed to use relative parent traversal, but reject empty, POSIX-absolute, drive-prefixed, backslash/UNC/device, and control-character forms on every host. Digest inputs use canonical Git index blob bytes whenever a tracked path is clean against the index, including CRLF-smudged checkouts and platforms that materialize a tracked symlink as an ordinary file. Genuinely dirty tracked paths and untracked paths use current working-tree bytes, so portable normalization cannot hide uncommitted delivery changes. Definition, project-freshness, acceptance, legacy reconstruction, archived-subtree, baseline, and trusted-transition comparisons share this byte-selection rule.

A tracked symlink whose index path is dirty and absent from the working tree is a `Missing` topology entry, not a request to read its historical target blob or a nonexistent filesystem path. Project freshness frames it as missing with mode zero; both manifest and legacy acceptance surfaces do the same. Clean tracked symlinks, including hosts that materialize them as regular files, continue to use the canonical index target bytes. This ordering keeps deletion distinct from both the previous symlink and a changed symlink target.

Portable symlink validation preserves exact accepted relative target bytes; it does not normalize away `./`, interior `./`, repeated separators, trailing separators, or `..` traversal. Those forms remain relative on every supported host. Validation rejects only the normative non-portable classes above, so topology evidence signs the target exactly as Git stores it.

Canonical index substitution is allowed only when Git can prove the path observable and clean. Assume-unchanged paths and materialized fsmonitor-valid paths fail closed through separate NUL-safe index-flag inspections. Skip-worktree paths are accepted only when absent, representing a clean sparse checkout whose canonical index blob remains authoritative; a materialized skip-worktree path fails closed. Any unmerged index stage fails closed. Before canonical substitution, a NUL-delimited `git check-attr` inspection rejects governed paths with an active custom `filter`, `working-tree-encoding`, or `ident`; standard text/eol normalization remains supported. This prevents performance flags, sparse materialization, merge state, or arbitrary clean/smudge transformations from hiding tested working-tree bytes.

Attribute inspection processes only exact evidence-relevant paths whose selected topology is a regular file, because Git content conversion does not transform canonical symlink target blobs or gitlink object IDs. Each bounded batch invokes `git check-attr` with NUL-delimited stdin and output, closes stdin before collecting the bounded result, validates successful process completion with stderr diagnostics, guarantees child reaping on every path, and parses exact path/attribute/value triples. The batch bound keeps both input and worst-case output below pipe capacity, preventing a child blocked on stdout from deadlocking a parent blocked on stdin while preserving deterministic path order and fail-closed error handling. Index visibility and attribute settings on unrelated excluded paths or safe symlink/gitlink modes do not block a digest that never signs converted regular-file content.

One candidate-scoped Git evidence read centralizes mode, object, stage, dirty-path, visibility-flag, sparse, and attribute inspection. It fingerprints the current index file and sorted split-index dependencies before and after that inspection, retries a bounded number of times when the authoritative index generation changes, and otherwise fails closed. This proves a stable index generation for the parsed evidence but does not claim an atomic filesystem or working-tree snapshot. Evidence parsing accepts at most 100,000 candidate paths, 4,096 bytes per path, and 64 MiB of aggregate path bytes before payload, owner, or attribute work. Attribute batches are independently bounded by path count and input/output bytes, and their NUL triples are parsed incrementally without an amplifying collection of borrowed fields.

Tracked symlink topology follows current state whenever Git reports the path modified. A current symlink signs its exact current target, a regular replacement signs current file bytes and executable mode, an absent path signs missing/mode zero, and another non-file signs non-file/mode zero. Historical index symlink mode and target bytes are used only for a genuinely clean path, including a platform-materialized clean symlink. The same classification feeds project freshness, manifests, and legacy acceptance aggregates.

Selected lifecycle definition artifacts must be regular files. Clean tracked index symlinks and dirty or untracked working-tree symlinks fail closed before payload reads, so an external referent can never become definition evidence. Definition artifact size limits then apply to the authoritative regular-file bytes that are signed. Clean tracked inputs are bounded after reading canonical index bytes, while dirty or untracked inputs retain a safe `symlink_metadata` pre-check before reading and are bounded again on the returned bytes. Checkout smudging therefore cannot reject a canonical artifact under the limit or admit canonical evidence over the limit.

Legacy archive snapshots enumerate the union of relevant tracked index entries and present working-tree entries rather than relying only on directory traversal. Absent sparse-checkout entries therefore remain represented by canonical index bytes, including the legacy baseline ledger. A dirty deletion or untracked absence of the authority baseline fails closed and cannot retain a prior definition binding; only a proven clean sparse absence reads the canonical index ledger. Dirty tracked symlinks inside an archive use the same current-topology classifier as project and acceptance evidence, so replacement by a file, deletion, or another non-file cannot inherit historical symlink mode.

`SemanticSuccessionEvidenceV1` uses its own `specsync.semantic-succession.v1` domain and explicit schema version. It permits at most 100,000 tuples; predecessor IDs and module names are bounded to 256 bytes and paths to 4,096 bytes. Tuples are strictly sorted and unique by `(numeric predecessor sequence, full predecessor ID, path, canonical module)` so acknowledged same-sequence collisions remain deterministic; paths are portable, modules are validated canonical identifiers, and old/new full-entry digests are lowercase 64-character SHA-256 values. Duplicate or conflicting keys fail closed. Closing evidence contains exactly one tuple for each approved supersedes obligation that acceptance proves and no tuple without a one-to-one approved obligation. Binding full-entry digests ensures chmod, file/symlink, missing/non-file, and gitlink topology transitions cannot alias byte-identical payloads.

Compare each signed entry with its current entry. An exact match needs no successor. A changed entry expands to one obligation for every signed canonical owner. Every obligation needs one terminal candidate with an exact signed succession tuple matching predecessor ID, path, that owner, old digest, and candidate's accepted new digest. The same candidate therefore binds path and module for each obligation; different candidates may satisfy different owner obligations or different entries. Numeric sequence can restrict candidates but does not prove succession; timestamps, lexicographic IDs, and scope overlap are never evidence.

Introduce two deliberately separate validation modes. Historical-integrity authentication applies to every archive and proves a unique location, trusted accepted-state projection and snapshot, definition, verification, manifest or uniquely reconstructed legacy aggregate, closing approval, and canonical succession tuples without comparing those signed inputs to today's workspace. Archived status serializes this as `authenticated-history` or `corrupt-history`. Recursive current-input validation starts only from active accepted roots; it compares their signed entries with the current workspace and evaluates an archived record recursively only when that archive is selected as a successor candidate. Active accepted status serializes `exact`, `successor-covered`, or `stale`. The two modes use separate memoization keys so historical authentication can never be reused as candidate-grade current validity.

Pre-CHG43 standalone archives require an explicit downgrade-safe baseline because they predate accepted-state snapshots and may use historical definition-digest semantics. Add `.specsync/archive/legacy-baseline.json` schema v1 with a fixed domain, authority change ID, exact release-branch cutoff commit, and strictly sorted unique entries of archive ID, canonical dated archive path, unique introduction commit, and canonical subtree digest. Add an omitted-when-absent `ChangeRecord.legacy_archive_baseline_digest`; supported definition approval binds the domain-separated canonical ledger bytes into the authority record before calculating the approval digest. The ledger path is an explicit CHG43 affected path, exact-only delivery input, and is also bound into CHG43's acceptance manifest and closing approval.

Authority is deliberately two-phase to avoid circular pre-acceptance strict failure. During Approved, Implementing, or Verifying, baseline authentication requires exact ledger bytes matching the authority's definition-bound digest, a valid authority definition approval, a canonical cutoff exactly equal to the authority's definition-bound base commit and ancestral to current history, and introductions at or before that cutoff. Once the authority is Accepted or Archived, baseline authentication upgrades and additionally requires its manifest-backed closing evidence, exact-owned ledger entry, trusted accepted/history anchor, and cutoff ancestry to that anchor. The bootstrap phase cannot survive an authority definition or ledger edit, and the post-accept phase cannot downgrade to definition-only authority.

Resolve the exact definition-bound base commit and require a canonical 40-hex identity. The cutoff must equal that base byte-for-byte, be ancestral to current history, and later be ancestral to the authority acceptance/history anchor. Each introduction commit must be ancestral to the cutoff and uniquely introduce the exact archive path absent from all parents. Recompute `specsync.legacy-archive-subtree.v1` from the complete current subtree using strictly framed normalized relative path, kind, mode, and payload bytes. Regular files and portable symlink targets are supported; gitlinks, non-files, extra/missing paths, type/mode changes, unsorted/duplicate entries, arbitrary ancestor/descendant/divergent or post-cutoff commits, unavailable objects, and zero/multiple introductions fail closed. The stored archived state identity, passed verification, and internal definition/closing records remain inspectable, but historical definition digests are not recomputed under today's schema.

Baseline authentication returns only standalone `AuthenticatedHistory`. It is never called from accepted-evidence authentication, legacy manifest reconstruction, transition proof, recursive candidate validation, archive preflight eligibility, reopen, acceptance, or closing, and modern manifest archives never use it. An archived record can cover an active predecessor only through the normal explicit supersedes edge, accepted-transition old/new proof, semantic delta, and recursively current candidate-grade evidence; a baseline entry alone can never mask stale active evidence.

The recursive candidate context contains all active and archived records, a visiting set, and memoized current-input results. A successor is eligible only when it is accepted or archived, is not no-spec, contains a valid non-empty semantic delta, is recorded in trusted current/default history, has valid definition and closing evidence, and its own acceptance inputs validate recursively. A cycle or corrupt candidate is invalid, never an alternate success path. Strict project checking authenticates every archive historically and runs recursive current validation only from active accepted roots; an unrelated archived input that evolved after archival remains historically valid and does not make the project red.

For legacy records with no manifest, first run the existing exact aggregate comparison. If stale, locate the trusted reachable commit that transitions the exact workspace state to accepted, reconstruct the covered Git-tree entries and owners from that accepted tree, apply the historical sequence-ledger rule, and reproduce the signed legacy aggregate. Later reachable commits with accepted state are deduplicated by canonical manifest/evidence bytes; identical results are not ambiguous, while distinct results fail closed. A legacy successor without signed tuples additionally requires a durable approved supersedes edge, a trusted definition-signed base commit ancestral to the unique accepted-transition anchor, exact old/new full-entry digests at those two trees, and a persisted semantic delta governing the bound module.

The status surface returns one structured reason with state-appropriate validity values: active accepted records use current exact/successor/stale validity, while archives use historical authenticated/corrupt validity. Every record is loaded through a location-aware workspace handle; all state, approval, verification, delta, and artifact reads use that discovered active or dated-archive directory. Duplicate active/archive IDs or ambiguous archive locations fail closed. Archive preserves accepted-state bytes authenticated by the unique trusted accepted-transition anchor and prior closing evidence; archive cannot mint a new human approval. It validates the archived projection against those bytes, then preflights an in-memory post-move index by authenticating the target history and recursively validating every active accepted root, which naturally reaches dependent archived candidates but ignores unrelated archive drift. A legacy archive without provable accepted bytes fails closed. Any post-move failure restores the exact original state and Markdown bytes, removes the staged snapshot, and restores the active location. This preserves immediate uncommitted check/status validity after the move.
