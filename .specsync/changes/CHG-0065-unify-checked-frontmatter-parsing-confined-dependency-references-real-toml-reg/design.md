# Design

## Architectural objective

Issues #413, #419, #422, #436, and #444 are one consistency and trust-boundary defect: the same
frontmatter and `depends_on` bytes currently pass through several permissive parsers and path
joiners, so `check`, `deps`, `score`, `resolve`, and MCP can disagree or report success without
having verified anything. CHG-0065 introduces one checked frontmatter boundary and one typed,
confined dependency-reference boundary, then makes every gating consumer use their structured
results.

The compatibility `parse_frontmatter(&str) -> Option<ParsedSpec>` API remains temporarily available
for non-gating callers, but it becomes a thin wrapper over the checked parser. It must never be used
to turn a diagnostic into an omitted spec, omitted edge, or successful gate.

## Exact issue-facet binding

| Issue | Binding owned by CHG-0065 |

| #419 | Wire `deps --require-coverage` through checked coverage in normal, JSON, Mermaid, and DOT modes; make `101` a nonzero usage result and zero-source discovery an inconclusive gate failure; reject scalar/map `depends_on`; deduplicate normalized edges; intentionally continue allowing syntactically valid unique unknown extension fields. |
| #422 | Fetch `.specsync/registry.toml` first and use root `specsync-registry.toml` only after a primary 404; attach `GITHUB_TOKEN` safely; make zero successful fetches and every unresolved remote outcome exit 1; honor JSON without human preamble. |

## Checked frontmatter model

`src/types.rs` owns the diagnostic vocabulary and dependency-reference value types. `src/parser.rs`
owns syntax extraction and typed frontmatter decoding.

```rust
pub struct FrontmatterDiagnostic {
    pub field: Option<String>,
    pub line: Option<usize>,
    pub kind: FrontmatterDiagnosticKind,
    pub message: String,
}

pub enum FrontmatterDiagnosticKind {
    MissingDelimiters,
    Syntax,
    DuplicateKey,
    InvalidType,
    InvalidShape,
    InvalidValue,
}

pub fn parse_frontmatter_checked(
    content: &str,
) -> Result<ParsedSpec, Vec<FrontmatterDiagnostic>>;
```

The checked parser SHALL:

- preserve the existing leading-BOM and CRLF compatibility behavior;
- reject duplicate top-level keys, including duplicate unknown extension keys, without selecting
  either value;
- require known scalar fields to have scalar values and known list fields to have list values;
- parse block and flow lists identically, including the flow-list form generated by SpecSync;
- report malformed quoting, arrays, indentation, tabs, and colon-less frontmatter content with a
  stable diagnostic kind and the best available line number;
- accept syntactically valid unknown top-level extension fields without adding them to
  `Frontmatter`;
- accept version values that serialize to the supported version string representation while
  rejecting booleans, maps, lists, and non-version text;
- validate `implements` and `tracks` as lists of non-negative issue numbers instead of silently
  dropping malformed entries; and
- preserve declaration order while deduplicating equivalent dependency identities after each raw
  entry has been validated.

Consumers that gate correctness use `parse_frontmatter_checked` directly. The compatibility
wrapper returns `None` on any checked error and is retained only while call sites are migrated; new
gating code must not call it.

## Typed and confined dependency references

One parser represents all supported dependency forms and retains the user's exact spelling for
diagnostics:

```rust
pub enum DependencyRef {
    LocalModule { raw: String, module: String },
    LocalSpec { raw: String, path: PathBuf, module: String },
    Remote { raw: String, repository: String, module: String },
}

pub enum DependencyRefError {
    Empty,
    MalformedRemote,
    InvalidModule,
    AbsolutePath,
    ParentTraversal,
    BackslashPath,
    InvalidSpecPath,
    EscapesProjectRoot,
}
```

`DependencyRef::parse` is syntax-only and platform-portable. It rejects empty values, absolute or
drive-relative paths, root/prefix components, `.` and `..`, backslashes, malformed `.spec.md`
paths, and malformed remote references. A remote reference is exactly `owner/repository@module`;
all three components are non-empty and validated before any URL construction. Raw text is never
normalized away in an error.

`DependencyRef::resolve_local(root, specs_dir, registry)` is the only local resolution path. It:

1. resolves a bare module through an explicit registry mapping first;
2. otherwise resolves it to the exact conventional
   `specs/<module>/<module>.spec.md` location;
3. resolves an explicit local spec path as project-relative only;
4. confines the mapping lexically and through existing-ancestor/canonical symlink checks beneath
   the canonical project root; and
5. returns a typed missing, malformed, or escape result instead of probing an outside path.

Normalized identity is used only for deterministic deduplication and graph edges. Diagnostics and
structured reports retain `raw`. The parser does not classify a string as “local” merely because a
malformed remote reference failed to parse.

Canonical specs at `specs/<module>/<module>.spec.md` must declare that same module identity.
Registry-mapped custom locations are valid and are checked against the registry's module key, not
against their parent directory name.

## Registry and authenticated GitHub transport

`src/registry.rs` deserializes registry bytes with the existing `toml` dependency. A valid registry
may use either:

- canonical `[registry]` plus `[specs]`, or
- documented `[registry]` plus repeated `[[modules]]` records containing `name` and `spec`.

Both shapes produce the same ordered `RegistryEntry`. Conflicting duplicate module mappings,
duplicate records, wrong field types, malformed TOML, unsafe paths, and missing required registry
identity fail closed. The inert 5.0.1 exception remains only for syntactically valid content with no
registry name and no effective mappings. `generate_registry` and `register_module` continue to
emit canonical `[specs]` TOML with safely serialized keys and values.

Callers preserve the established user-facing failure shape
`failed to parse local registry <path> while resolving <module>` (with the real path and module in
place of placeholders). A standards-parser detail may be attached as structured context, but it
must not replace that compatibility diagnostic or allow fallback resolution.

Remote registry and spec reads share one bounded GitHub content-fetch implementation in
`src/github.rs`; authentication logic is not duplicated in `registry.rs`. The transport:

- validates `owner/repository` before URL construction;
- sends `GITHUB_TOKEN` as an authorization header when present and never includes the token in a
  URL, cache key, diagnostic, debug output, or fixture snapshot;
- requests `.specsync/registry.toml` first and tries root `specsync-registry.toml` only after an
  actual 404 from the primary path;
- does not hide 401, 403, timeout, malformed response, or other transport failures behind the
  legacy fallback;
- bounds response bytes and individual operations; and
- fetches unique repositories with bounded parallelism under one invocation deadline rather than
  paying a sequential timeout per reference.

Remote spec paths come only from a successfully parsed and confined registry entry. The cache is
versioned by repository, path, and validation schema; cached and live content pass through the same
checked parser so warm and cold results are semantically identical.

## Shared reports and command outcomes

Dependency graph construction returns a checked graph report, not a permissive graph plus a side
channel. Parse, identity, confinement, registry, coverage, and I/O diagnostics remain attached to
the report. Text, JSON, Mermaid, and DOT renderers all consume this same validated report; a
visualization cannot bypass a gate by rebuilding the graph through the compatibility API.

`deps --require-coverage N` uses `compute_coverage_checked`. It applies the threshold in every
output mode, rejects out-of-range thresholds as usage errors, and treats zero-source or malformed
manifest discovery as inconclusive rather than vacuously passing. JSON adds at least `valid`,
`gate_passed`, `coverage`, `errors`, and `warnings`; duplicate dependency declarations produce one
edge and one rendered line.

`resolve` accumulates a typed `ResolveReport` containing every raw reference and its outcome.
Missing local specs, malformed references, unsafe paths, registry-fetch failures, absent remote
modules, unparseable or unavailable remote specs, and zero-success remote verification all set
`valid: false`. “Verified — no drift” is legal only when at least one requested registry was
successfully fetched and every requested reference was verified. `--strict` promotes advisory
compatibility findings such as a non-bidirectional remote reference; it does not determine whether
an unresolved reference is already an error. JSON output contains `valid`, `gate_passed`, per-ref
outcomes, cache provenance, and diagnostics and contains no human preamble.

The process contract is uniform:

| Exit | Meaning |
|------|---------|
| `0` | Complete trustworthy success, or an explicitly advisory run with no failed requested gate |
| `1` | Validation finding, unresolved reference, remote/coverage inconclusive result, or failed gate |
| `2` | CLI usage error such as an unsupported format or out-of-range threshold |

## Check, scoring, and MCP parity

`validate_spec`, dependency graphing, freshness scoring, and resolution use the same parsed
`DependencyRef` values. Valid bare modules, registry-mapped specs, and remote references do not
receive stale-path penalties. Malformed or escaping references produce the same core diagnostic
kind and raw value everywhere, although each renderer may add command context.

MCP adopts the checked parser and dependency-reference APIs only after the #414 confinement branch
is integrated. It keeps the retained server-root capability as the outer authority boundary;
CHG-0065 does not replace or weaken MCP's root preflight. MCP resources, graph output, checks,
coverage, and scoring surface malformed/escaping dependencies as tool or resource errors with
structured `valid`/`gate_passed` data rather than silently omitting them.

## Delivery order and ownership boundaries

1. Add checked parser diagnostics and typed `DependencyRef` in `types`/`parser`.
2. Replace registry scanning and add the shared authenticated content transport.
3. Migrate dependency graph and coverage gating; this may proceed alongside registry transport
   after the foundation is stable.
4. Migrate validator, the `check` command, and scoring, including module identity and
   registry-mapped paths.
5. Replace resolve accumulation/rendering and add bounded repository concurrency.
6. Wire CLI arguments, formats, and exit outcomes; add end-to-end parity fixtures.
7. Migrate MCP last, after #414 lands, to avoid overlapping security edits.

`src/main.rs`, `src/cli.rs`, `src/commands/mod.rs`, `src/commands/check.rs`, check/command
integration fixtures, and `CHANGELOG.md` have one integration owner. No slice may reintroduce a local dependency parser,
registry scanner, or direct `root.join(dep)` validation path.
