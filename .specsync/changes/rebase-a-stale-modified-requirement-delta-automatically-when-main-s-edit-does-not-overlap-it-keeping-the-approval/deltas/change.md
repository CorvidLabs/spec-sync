## ADDED

### REQUIREMENT REQ-change-161

When `change check` finds a `## MODIFIED` requirement item of a workflow-v2 change whose canonical block moved after the item was approved (REQ-change-122), or whose block main has edited since the item's base, it SHALL try to rebase the item before refusing (#1085). Main's block SHALL be read from Git, never from the working tree: it is the requirement's block at the merge-base of HEAD and the default branch (`origin/HEAD`, else `origin/main` or `origin/master`), that commit SHALL be on the default branch's first-parent line, and main has edited the item only when that block differs from the item's base and from the delta's body, and that line held the base earlier. It SHALL take the base's text from that line and merge it, main's block and the delta's body word by word, aligning them only on words that occur once in each of the three. It SHALL rebase only when the working tree's block is main's block, the delta's body, or already their merge. An item it cannot rebase SHALL be refused as REQ-change-122 refuses, writing nothing: when the edits overlap (a stretch both sides changed that no such word splits, or a word both sides deleted at one place that one side adds at another, as when both move one word), when a text it needs cannot be read from Git or there is no default branch, when the module's delta is over 256 KiB or the change already holds 64 rebase records, or when the working tree's block is any other text, such as a sentence only the change's branch holds or an older text of main's. The same holds for an item whose working tree block already carries the change's own body: it is refused when main has edited it and it cannot be rebased, since keeping that body drops main's edit, and when a default branch exists and Git cannot read the merge-base, tree, text or history the check needs for it; with no default branch, and in CI, such an item is read as one main has not edited, as before. When one item of a change cannot be rebased, no item is rebased and nothing is written. A rebase SHALL rewrite the item's body in the delta to the merge, so the canonical requirement becomes the merge, append a rebase record to the change's `approvals.json` under `delta_rebases`, and keep the definition approval. A rebase record SHALL hold the base block, main's block, the commit main's block was read at and the delta before the rebase, so every reader recomputes the merge and its digests instead of trusting the record. While the change is delivered, every reader also checks that the commit is on the default branch's first-parent line, is in HEAD's history, holds the main block, and that the line held the base block earlier. The effective approval then binds the rebased delta and main's block as the item's base, so main's next edit to the requirement is found the same way and rebased over the last rebase's main block, or refused. A record that does not recompute, or fails those checks, is refused by `change check` and named by `change status`.

Acceptance Criteria
- Main edits a requirement after approval and the change rewords another part of it: once the branch has merged main, `change check` rebases the delta, the canonical requirement carries both edits, the approval stays valid with no `change approve`, and `approvals.json` holds one rebase record naming the merge-base commit.
- A change materialized before main's edit that then merged main is rebased whether Git merged the requirement cleanly or the conflict was resolved to main's side or to the change's side.
- A second main edit after a materialized rebase is rebased again over the last rebase's main block.
- Main and the change edit the same words, one side adds back elsewhere a word both sides deleted at one place (base `a b c`, main `a c`, approved `b a c`), or both sides move one word to different places (base `a b c d`, main `b a c d`, approved `a c b d`): `change check` refuses as today, naming the requirement and `specsync change approve <id>`, and writes nothing, also when the branch kept its own text in the merge.
- A word only one side deleted that the other side's new text uses elsewhere still merges (the change drops one `the`, main appends a sentence with `the`), and so does a word only one side moves.
- Edits that a repeated word could align two ways (base `c a b d`, main `b b d`, approved `b d`) are refused as an overlap.
- A sentence only the change's own branch holds, before the first check, after materialization or in a merge resolution, is refused as stale and never merged into the delta, and nothing is written.
- A working tree holding an older text of the requirement than the approval-time text, or a side branch's text that its merge into the default branch did not keep, is refused, not merged.
- With one stale requirement that merges and one that overlaps, `change check` refuses, and the deltas, the canonical requirements and `approvals.json` stay byte for byte.
- A change merged into the default branch before it is finalized (#654), whose block there is its own body, is neither refused nor rebased by `change check --commit` or `change audit` on that branch, and no rebase is recorded.
- A rebase record that does not recompute, or whose commit is not on the default branch's first-parent line, is not in HEAD's history or does not hold its main block, is refused by `change check`, and text `change status` names it.
- A `## MODIFIED` spec section, a `## REMOVED` item, a workflow-v1 change, a CI run, a text Git cannot read, a repository with no default branch, a delta over 256 KiB and a change holding 64 rebase records each keep today's refusal.
- With a default branch, an item whose working tree block already carries the change's own body and whose main text Git cannot read is refused, naming the requirement; with no default branch, and in CI, it materializes as before.

## MODIFIED

### REQUIREMENT REQ-change-122

A definition approval SHALL record, for every `## MODIFIED` and `## REMOVED` delta item, a digest of the canonical block it was approved against. When such an item is not already applied and its canonical block no longer matches that recorded base, `change check` SHALL refuse before writing any canonical file and `change audit` SHALL report the same refusal, unless REQ-change-161 rebases the item first. The refusal SHALL name the module and block and SHALL name rewriting the delta body onto the current canonical text, `change approve` and `change check` as the remedy. An approval that recorded no bases is unknown, not violated, and keeps materializing as before.

Acceptance Criteria
- A stale MODIFIED item whose block main rewrote after approval, with edits that overlap the change's own, is refused by `change check`, both before and after the first materialization, and the canonical file keeps main's bytes.
- `change audit` reports the same refusal for that change.
- The refusal names the module, the requirement or section, and `specsync change approve <id>`.
- A rebased and re-approved delta materializes, keeping the other change's text it now carries.
- A block main changed that this change does not touch is not refused.
- An approval without recorded bases keeps materializing as before.
