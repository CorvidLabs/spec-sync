# Design

- **Main's block comes from Git, at the merge-base** (fable-lead's, Codex's, ss-lead's and the tester's reviews of #1089). Main's block is the requirement's block at `git merge-base HEAD <default>` (`origin/HEAD`, else `origin/main` or `origin/master`), and that commit must be on the default branch's first-parent line. Main has edited the item only when that block differs from the item's base and from the delta's body, and the line held the base earlier (newest 200 commits that touched the file). The base text is read from that line too. A block equal to the delta's body is the change's own text: after a change is merged before it is finalized (#654), HEAD is the default branch and holds it.
- **Three working-tree texts.** A rebase happens only when the working tree's block is main's block, the delta's body, or already their merge. That covers a change rebased before materialization, a change materialized before main's edit that then merged main (cleanly, or resolved to either side), and a second main edit after a materialized rebase. Any other text, such as a sentence only the branch holds, an older text of main's, or a side branch's text its merge did not keep, keeps the refusal. Until the branch merges main, the merge-base still holds the base, and nothing is rebased.
- **Where.** `change check` (`materialize_change_deltas_inner`), after the delta-body binding check and the dependency, conflict and open-task gates, and before the base check, outside CI. On a clean merge, the rebased delta, the canonical requirement (when the working tree carries the delta's body) and the rebase record are written in one prepared transaction. If any item is left stale, nothing is written. The base check then also refuses a workflow-v2 requirement main has edited past its effective base, even when it is applied, so a merge that kept the change's text over an overlapping main edit is not silently accepted. With a default branch, an applied requirement whose merge-base, tree, text or history Git cannot read is refused, naming why; with no default branch, and in CI, it is read as unedited, as before (Codex's third review, as ss-lead narrowed it).
- **Merge.** Tokens are a word with its trailing whitespace. Anchors are words that occur exactly once in each of the three texts, chained in rising order and found again inside each gap. Between anchors, a chunk takes the side that changed. Both sides changing to different text is an overlap and refuses. A word both sides removed from one stretch the same way that one side alone adds in another is a move against the other side's edit and refuses too; that covers a move against a deletion and both sides moving one word to different places (Codex's second and third reviews). A word only one side deleted may appear in the other side's new text. Refusing every once-only word out of order (R1) was measured on the seven stale triples rebuilt from Chough's history and rejected: it refused #360's REQ-cli-012, where main alone moved a clause; without it six of seven rebase and #336 is an overlap. A side over 4,000 tokens refuses.
- **Record** (`approvals.json` `delta_rebases`, append-only, omitted when empty): schema 1, module, item key, the extended approval's index, timestamp and digest, the time, the base block, main's block, main's commit, the module delta before the rebase, and the rebased delta's digest. A delta over 256 KiB, or a change already holding 64 records, is not rebased.
- **Readers of a delivering change** check each record's commit: on the default branch's first-parent line, in HEAD's history, holding the main block, after a text holding the base block. An accepted or archived change is not re-judged against a default branch that has since moved on.
- **Effective claims.** `effective_delta_claims(approval, ledger)` starts from the approval's delta digests and bases and folds every record anchored to it, in order. For each record it checks that the pre-rebase delta has the current digest, that the base block has the current base, recomputes the merge and the rebased delta, and checks that digest. Then it moves the module's digest and the item's base to main's block. Any mismatch is an error naming the record. The binding read, the base check, re-approval's previous claims and acceptance's normalizing approval all read the effective claims.
- **Status.** `change status` prints each rebase under the effective approval and lists them in JSON as `summary.delta_rebases`; when a record is refused, text status prints the refusal naming it.
- **Rejected:** rewriting the delta and re-recording an approval in the human's name (that would be an approval nobody gave); storing only digests in the record (the record would then be a bare claim that could launder any body); rebasing spec sections and REMOVED items (#1085 names requirements; sections can follow).
