# SpecSync 6.4.0 preparation

Status: **in preparation**. No tag, release or publish has happened. Leif set what 6.4.0 holds
and the order of its steps (Claude Code chat with his planning session, 2026-11-19), and approved
this preparation's definition on 2026-11-20, relayed by his planning session. This file is the
release handoff record.

6.4.0 is a minor release. Since 6.3.0, `main` adds a command and an option, and changes an exit
code:

- `specsync history <module>`, with each shipped change recorded in its own history fragment
  (#1086, #1088);
- `change approve --dry-run` (#1100);
- `change ship-status` exits 1 when it reports a blocker (#1093).

Under SemVer that is 6.4.0, not 6.3.1.

6.4.0 also carries the fix for GHSA-7q5v-8jcc-rx54, built privately and merged before the tag.
Running SpecSync in a repository you do not trust could overwrite files outside it through a
symbolic link the repository committed, run a command through Git's config by replaying a
transaction journal the repository shipped, report a forged pass from a hash cache the
repository shipped, or hang or run out of memory on a FIFO, a device or an oversized file. In
6.4.0, every project read and write goes through a confined, bounded handle, and SpecSync keeps
its hash cache, transaction journal, remote spec cache and change read cache only in the user's
cache folder, never in the work tree or a Git directory. `CHANGELOG.md` `### Security` under
`[6.4.0]` lists each part. Leif reviewed the fix as one review of its last four changes (Pass,
2026-11-20, relayed), after an independent re-check found no high-severity hole a plain command
can reach.

## Upgrade notes

- **The security fix changes what you see in five places:**
  - **The first `check` after upgrading validates every spec.** The hash cache moved to the user's
    cache folder (`$XDG_CACHE_HOME`, else `~/Library/Caches` on macOS or `~/.cache`, under
    `specsync/projects/`). The old `.specsync/hashes.json` and `.specsync-cache/` are never read;
    you can delete them.
  - **A `.specsync/change-transaction.json` in the work tree stops every lifecycle command** with
    its path, until you check the files it lists and delete it. SpecSync 6.3.0 left one there
    only after an interrupted write.
  - **A user cache folder inside the project is refused.** This happens in CI that sets `HOME` or
    `XDG_CACHE_HOME` to the checkout. `check` warns once and validates every spec, and lifecycle
    (`change`) commands stop until `XDG_CACHE_HOME` points outside the project.
  - **Links.** A link that stays inside the project is still followed, unless it leads into the
    Git directory. An absolute link is refused even when it points inside. A link that leaves,
    a dangling link and a non-regular file are refused with the path named.
  - **Configured folders and sizes.** `specs_dir`, `source_dirs` and `schema_dir` must be relative
    paths inside the project. Reads are bounded: 4 MiB for state, 8 MiB for specs and source,
    64 MiB for whole inputs.

- **History fragments: move every lifecycle writer and every CI pin to 6.4.0 together.**
  `change check` now records each change it materializes in `specs/<module>/history/<change-id>.md`
  and no longer adds a Change Log row or bumps `version:` (#1084). We ran released 6.3.0 and this
  release's build on one fixture, a branch that ships a change with 6.4.0 against an
  `origin/main`:
  - 6.3.0's `specsync check` passes on a tree with fragments; it ignores them.
  - 6.3.0's `change audit` and `change audit --strict` fail on a branch whose changes add a
    fragment, at the checked tip and at the archive tip: "meaningful changed paths are not covered
    by an active change: specs/<module>/history/<id>.md". On a branch that only holds fragments
    already merged they pass.
  - So CI pinned at 6.3.0 fails `change audit` and `change audit --strict` on every pull request
    whose change was checked with 6.4.0. Raise every lifecycle writer and every CI pin to 6.4.0
    together, after publication, as 6.3.0's notes said for its own case.
  - The Action's default stays 6.3.0 until the post-publication change, and the immutable
    `@v6.4.0` tag embeds that default. Pass `version: '6.4.0'` yourself: always with `@v6.4.0`,
    and with any other wrapper until the post-publication change moves its default.
- **A 6.3.0 `change check` on a change that 6.4.0 recorded records it twice.** It adds a Change
  Log row and bumps `version:` (with `--commit`, it commits both). 6.4.0's `specsync check` then
  fails: "history fragment `specs/<module>/history/<id>.md` records `<id>`, and the Change Log in
  `specs/<module>/<module>.spec.md` records it too; keep one of the two records". The way out, as
  run:
  1. Remove the Change Log row 6.3.0 added for the change, and keep the fragment. 6.4.0's `check`
     passes.
  2. Put `version:` back to its value before the bump, so the spec is what 6.4.0 wrote. `check`
     still passes.
  3. Commit, then run `specsync change check <id> --commit` with 6.4.0, as `change status` asks
     ("the tree moved after the last check"). It passes, and so does `change audit --strict`.
- **`change ship-status` exits 1 when it reports a blocker**, for one change and for the roster
  (#654). It used to exit 0 beside its `Blocker:` line. The whole report is still printed first,
  and `--json` output stays one document. A change that is not ready but has no blocker, such as
  one still waiting for its review, exits 0 as before. A script that runs `ship-status` under
  `set -e` now stops at a blocked change.
- **`change approve <id> --dry-run`** says whether the approval would be accepted, and writes
  nothing (#1091). It exits 0 when no check refuses and 1 when one does. With `--json` it prints
  one document with `id`, `dry_run`, `would_approve` and `checks`: thirteen checks in approval
  order (`relay`, `lifecycle_lock`, `change`, `sequence`, `state`, `roster`, `baseline`,
  `definition`, `deltas`, `ownership`, `verification_ignored_paths`, `approval_record`, `actor`),
  each with `check` and `result` (`passed`, `refused` or `skipped`). A refused check carries its
  `message`, and a skipped one names the check it waits on in `skipped_because`. A refused
  `definition` or `ownership` check whose message names the `specsync change answer` command that
  fixes it carries that command as `fix`, as plain text. The command may hold a placeholder, such
  as `"<observable outcome>"`, so it is not safe to run as printed: fill it in, or show it to a
  person.

## The release lane

`release.yml` and `rc-assets.yml` are unchanged since 6.3.0. See [RELEASING.md](../RELEASING.md).

- An annotated `v6.4.0-rc.N` tag push qualifies the candidate on Ubuntu and macOS. It creates no
  release and no binaries.
- Promotion (`workflow_dispatch` with `rc_tag`) mints immutable `v6.4.0`. It then builds six
  archives, each Linux one checked by `linux-baseline.py`, and publishes a non-prerelease release,
  which moves `releases/latest`: twelve assets with the `.sha256` sidecars.
