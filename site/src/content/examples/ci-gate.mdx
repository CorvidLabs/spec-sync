Add the `spec-sync` GitHub Action to your workflow and any pull request that introduces spec drift will fail the check before it merges.

## 1. Add the action

```yaml
# .github/workflows/spec-sync.yml
name: specsync check
on: [pull_request]

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: CorvidLabs/spec-sync@v6.0.0
        with:
          version: '6.0.0'
          strict: true
```

Pin both the Action ref (`uses: CorvidLabs/spec-sync@v6.0.0`) and the binary (`version: '6.0.0'`). The immutable `@v6.0.0` Action tag still defaults omitted `version` to `6.0.0-rc.14`. With `strict: true` the action installs `specsync` and runs `specsync check --force --strict`.

## 2. Pin the spec-sync version

Keep the dual pin while validating 6.0.0 so an unintended upstream change cannot break a Friday-afternoon merge:

```yaml
- uses: CorvidLabs/spec-sync@v6.0.0
  with:
    version: '6.0.0'
```

The Action follows the spec-sync release cadence. Match the version you `cargo install` locally.

## 3. Tune the failure threshold

The Action `strict` input defaults to `false` (errors fail; warnings do not). For teams onboarding spec-sync incrementally, start there:

```yaml
- uses: CorvidLabs/spec-sync@v6.0.0
  with:
    version: '6.0.0'
    strict: false
```

There is no `score_threshold` Action input. Real inputs are `version`, `download-base-url`, `strict`, `require-coverage`, `root`, `args`, `lifecycle-enforce`, `comment`, and `token`. To fail when any spec scores below a floor, run `specsync score` after the Action has put `specsync` on PATH:

```yaml
- uses: CorvidLabs/spec-sync@v6.0.0
  with:
    version: '6.0.0'
    strict: false
- run: specsync score --min-score 60
```

Drop `strict: false` once your team is happy with the warning count, and raise `--min-score` as spec quality improves. Extra `specsync check` flags can go in `args` (whitespace-separated; no shell quoting).

## 4. Surface drift as PR comments

There is no `annotations` Action input. Set `comment: true` so the Action posts or updates a SpecSync pull-request comment:

```yaml
jobs:
  check:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      pull-requests: write
    steps:
      - uses: actions/checkout@v4
      - uses: CorvidLabs/spec-sync@v6.0.0
        with:
          version: '6.0.0'
          comment: true
```

A job-level `permissions` block zeros unspecified scopes, so `contents: read` has to sit next to `pull-requests: write` or `actions/checkout` fails on a private repo. The event must be `pull_request`. The comment body comes from `specsync comment`. A PR that adds an undocumented export then shows that finding on the PR instead of only in the Action log.

## 5. Bypass for emergency hotfixes

When you genuinely need to ship a fix without updating the spec (and you're not lying to yourself), opt out per-PR with a label:

```yaml
- uses: CorvidLabs/spec-sync@v6.0.0
  with:
    version: '6.0.0'
  if: ${{ !contains(github.event.pull_request.labels.*.name, 'skip-specsync') }}
```

The label adds friction (you have to consciously apply it) without being a hard block. Track the labels: if `skip-specsync` shows up more than twice a month, the team probably wants a real workflow change, not an escape hatch.
