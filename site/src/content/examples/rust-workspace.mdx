This walkthrough takes a Cargo workspace from drift to in-sync in eight commands.

## 1. Check what's drifted

```bash
specsync check
```

Running `specsync check` from the workspace root reads every `*.spec.md` file and validates it against the source code in each crate. Any export that's documented but missing from the code — or present in the code but absent from the spec — is reported.

## 2. Inspect the drift report

For a workspace with `api`, `core` and `cli` crates, each with its spec under `specs/`:

```
specs/api/api.spec.md
  ✓ Frontmatter valid
  ✓ All source files exist
  ✓ All required sections present
  ⚠ 1/2 exports documented
  ⚠ Undocumented export 'delete_user' from crates/api/src/lib.rs
  ✓ All dependency specs exist

specs/cli/cli.spec.md
  ✓ Frontmatter valid
  ✓ All source files exist
  ✓ All required sections present
  ✓ 1/1 exports documented
  ✓ All dependency specs exist

specs/core/core.spec.md
  ✓ Frontmatter valid
  ✓ All source files exist
  ✓ All required sections present
  ✓ 2/2 exports documented
  ✗ Spec documents 'Config::merge' but no matching export found in source
  ✓ All dependency specs exist

3 specs checked: 2 passed, 2 warning(s), 1 failed
File coverage: 4/4 (100%)
LOC coverage:  5/5 (100%)
```

Each finding names the spec, the export and the direction of the drift. An export the code has
and the spec lacks is a warning (an error under `--strict`); one the spec documents and the code
lacks is an error.

## 3. Auto-generate missing spec entries

```bash
specsync check --fix
```

`specsync check --fix` deterministically writes review rows for undocumented exports into the relevant `*.spec.md` files. Replace the generated prompts with final descriptions before committing.

## 4. Resolve phantom references

For `Config::merge` — a method referenced in the spec but removed from the code — you need to decide: restore the method or update the spec. Editing the spec directly is fine:

```bash
# Remove the stale `Config::merge` row from specs/core/core.spec.md
specsync check   # should now show 0 errors for that crate
```

## 5. Validate cross-crate references

```bash
specsync deps
```

`specsync deps` validates the dependency graph between spec files across crates. Add `--mermaid` or `--dot` when you want a rendered graph format.

<Callout type="tip">
  **Tip:** `specsync deps --mermaid` shows which crates depend on which spec files, so you know what to update first when a shared type changes.
</Callout>

## 6. Run CI-clean check

```bash
specsync check --strict
```

`--strict` exits non-zero on any warning, not just errors. Use this in CI so drift never reaches `main`.

## 7. Tag the release

Once everything is clean, your normal release flow applies. The spec is already committed alongside the code — no separate docs-deploy step needed.

## 8. Verify the final state

```bash
specsync check --strict
# 3 specs checked: 3 passed, 0 warning(s), 0 failed
```

That's the eight-command path from "spec drift everywhere" to a clean workspace, end to end. From here you do what you'd do in any Cargo workspace: bump the version, run the release lane, push the tag. The spec is part of the source tree, so it shipped with the commit you tagged — no separate docs-deploy step, no out-of-band sync.

Once you're past the initial cleanup, the rhythm is much shorter: `specsync check` runs in your normal pre-push hook (or in CI via the [GitHub Action walkthrough](/spec-sync/examples/ci-gate)), `specsync check --fix` adds review rows for new exports, and `specsync deps` catches cross-crate type ripples before they bite a downstream caller.
