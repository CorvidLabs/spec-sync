# Testing

Unit tests cover IDs, requirement grammar, semantic application, unsafe command rejection, adaptive policy, stale approvals, conflicts, and the full acceptance/archive path. CLI integration tests cover JSON interviews, rationale enforcement, dry-run adoption, and new-project enablement. Release validation runs the full Rust, spec, docs, audit, and build matrix.

## Artifact completeness and the canonical stripper (#716)

- `an_artifact_that_is_only_frontmatter_with_a_padded_opening_delimiter_is_incomplete` — DISCRIMINATOR. A trailing space on the opening `---` left the YAML in the body, where the gate counted it as prose and approved an artifact with nothing written in it. Fails on unfixed `main`.
- `a_padded_closing_delimiter_does_not_delete_the_prose_above_a_body_horizontal_rule` — DISCRIMINATOR, the destructive half. A trailing space on the closing `---` sent the scan to the first horizontal rule in the body, so a written design was refused as incomplete with nothing on screen to explain it. Fails on unfixed `main`.
- `a_bom_prefixed_artifact_with_no_written_body_is_incomplete` — CHARACTERIZATION. Passes on unfixed `main`; it records the third bug #715 fixed without claiming, back when this module's own stripper had no BOM trim and a BOM-prefixed empty artifact passed the gate.
- `a_four_dash_opener_still_hides_an_empty_artifact_from_the_gate` — CHARACTERIZATION of a KNOWN RESIDUAL. It asserts a wrong verdict on purpose: `----` is a Markdown thematic break, and accepting it as a delimiter would cut real bodies at their first rule. If it ever fails, check the reason and delete it — do not restore the behaviour.

- `REQ-change-091`: two end-to-end discriminators through the shipped binary, one honestly labelled control, and seven unit tests over the derivation and the notice, including the Cargo-config, `CARGO_HOME`, `[env]`-table and `build-dir` silence cases. `a_held_cargo_build_lock_is_named_before_verification_blocks_on_it` holds BOTH profile locks from the test process for the whole run — `flock` treats a second open file description as a foreign holder, so the blocked state is fixed rather than timed — and requires verification to name `target/debug/.cargo-lock` and not `target/release/.cargo-lock`; unfixed, stderr is empty. `a_verification_child_runs_in_its_own_process_group` has the child record its own PID and PGID and exit; unfixed, the two differ because the child inherits the parent's group. The control, `an_unheld_cargo_build_lock_is_not_reported_during_verification`, passes on the unfixed binary too, and it is what makes the notice's silence readable: a healthy four-minute compile must print nothing. `a_cargo_config_that_moves_the_build_directory_resolves_no_lock` exists because the first version of this change asserted that silence in a canonical spec without implementing it; it now reads the files Cargo merges, and its own control proves a config setting no layout key does not silence the notice. One assertion was deleted rather than widened after it flaked on the first `change check`: requiring the notice to stop once the lock is released is not observable at a deterministic instant, because a `flock` duplicated into a concurrent `fork` outlives the releasing thread's `drop` until that child execs. NOT covered by any test: that a `SIGINT`/`SIGTERM` delivered to a live parent asynchronously ends the group. Asserting it means racing a real signal against a real process death, which is the wall-clock gate #707 documents the cost of; the structural precondition is asserted instead and the delivery path is left stated rather than claimed.

- `REQ-change-092`: four discriminators and one control, every one judged against a binary built from a SEPARATE clean checkout of unfixed `main`. `a_delta_corrected_after_materialization_reaches_the_canonical_spec_on_the_next_check` is the filed defect: unfixed, the second `materialize_change_deltas` returns `Ok`, writes nothing, and the spec keeps the first delta's wording. `a_materialized_spec_missing_its_version_bump_and_change_log_row_gets_both_back` is the widening, and it is why re-applying the delta alone would not have been a fix — the fixture is the #721 shape, built by deleting exactly the bump and the row from a spec that has all three outputs. `a_corrected_delta_re_materializes_over_a_block_its_own_earlier_run_removed` guards the trap under the fix: `apply_markdown_block` refuses to remove a block that is not there, so a re-materialization that does not separate 'already applied' from 'cannot be applied' turns the silent skip into a hard error on every corrected `## REMOVED` delta. `the_refusal_for_a_changed_delta_names_the_second_step_that_finishes_the_job` pins the diagnostic, which named only `approve` — the action that recorded a new digest, satisfied the #711 gate and triggered the skip. The control, `re_approving_a_byte_identical_delta_leaves_the_canonical_spec_byte_for_byte_alone`, passes on the unfixed binary too and is the important half: 'always re-materialize' satisfies all four discriminators and would rewrite every canonical spec, re-bump every version and append a second Change Log row on every `check`. It asserts the spec AND the requirements are byte-identical, the version stands at one bump, and the Change Log carries exactly one row. Blast radius measured rather than argued: all 208 `state.json` under `.specsync/` (193 with `canonical_applied: true`) and all 208 `approvals.json` deserialize and round-trip unchanged — no field was added, so no persisted shape and no definition digest moved — and 446 of 454 archived (change, module) pairs carry a Change Log row naming the change, which is what makes the row usable as per-module materialization evidence.
